# Лабораторная работа 2. Потоки. Процессы. Асинхронность

## Цель работы

Цель лабораторной работы — изучить отличия между потоками, процессами и асинхронным программированием в Python, а также сравнить их применение на вычислительных и сетевых задачах.

## Использованные подходы

| Подход | Модуль/технология | Особенность |
|---|---|---|
| threading | `threading` | параллельное выполнение потоков внутри одного процесса |
| multiprocessing | `multiprocessing` | запуск нескольких процессов, обход GIL для CPU-bound задач |
| async | `asyncio`, `aiohttp` | асинхронное выполнение I/O-bound задач без создания отдельных потоков |

## Задача 1. Сумма чисел от 1 до 10000000000000

В первой задаче были написаны три программы, использующие `threading`, `multiprocessing` и `asyncio`. Каждая программа разбивает общий диапазон чисел на несколько поддиапазонов и считает частичные суммы.

Чтобы программа не выполнялась слишком долго, сумма внутри каждого диапазона считается по формуле арифметической прогрессии. При этом требование разделения задачи на несколько параллельных частей сохраняется.

Итоговая сумма:

```text
50000000000005000000000000
```

Проверка корректности во всех трёх вариантах показала:

```text
Результат корректный: True
```

### Результаты выполнения задачи 1

| Подход | Количество задач | Время выполнения |
|---|---:|---:|
| threading | 8 | 0.001214 сек. |
| multiprocessing | 8 | 0.161984 сек. |
| asyncio | 8 | 0.000103 сек. |

### Комментарий по результатам

В данной реализации быстрее всего выполнился вариант с `asyncio`, потому что каждая подзадача выполняет очень короткое вычисление по формуле, а накладные расходы минимальны. Вариант `multiprocessing` оказался медленнее из-за стоимости создания процессов, особенно заметной на Windows. Для реальных тяжёлых CPU-bound вычислений процессы обычно лучше потоков, но в этой задаче вычисление было оптимизировано формулой.

## Задача 2. Параллельный парсинг веб-страниц

Во второй задаче были реализованы три программы для параллельной загрузки веб-страниц, извлечения заголовков и сохранения данных в базу данных из первой лабораторной работы.

Использованные URL:

```text
https://example.com/
https://www.python.org/
https://fastapi.tiangolo.com/
https://www.postgresql.org/
https://docs.sqlalchemy.org/
https://www.djangoproject.com/
```

Данные сохраняются в существующую таблицу `tag`, так как проект первой лабораторной является тайм-менеджером, а заголовки страниц можно использовать как автоматически собранные теги/источники.

### Результаты выполнения задачи 2

| Подход | Количество URL | Время выполнения |
|---|---:|---:|
| threading | 6 | 1.350174 сек. |
| multiprocessing | 6 | 1.659131 сек. |
| asyncio + aiohttp | 6 | 1.458582 сек. |

### Полученные заголовки

| URL | Заголовок |
|---|---|
| `https://example.com/` | Example Domain |
| `https://www.python.org/` | Welcome to Python.org |
| `https://fastapi.tiangolo.com/` | FastAPI - FastAPI |
| `https://www.postgresql.org/` | PostgreSQL: The world's most advanced open source database |
| `https://docs.sqlalchemy.org/` | SQLAlchemy Documentation — SQLAlchemy 2.0 Documentation |
| `https://www.djangoproject.com/` | The web framework for perfectionists with deadlines \| Django |

### Комментарий по результатам

В задаче парсинга основное время занимает ожидание сетевых запросов и запись в базу данных. Поэтому `threading` и `asyncio` хорошо подходят для такой задачи. В конкретном запуске `threading` оказался немного быстрее, но разница небольшая и зависит от скорости ответа сайтов и состояния сети. `multiprocessing` показал большее время из-за накладных расходов на создание процессов.

## Вывод

В лабораторной работе были реализованы и сравнены три подхода к параллельному и асинхронному выполнению задач. Для коротких вычислений создание процессов может быть неоправданным. Для сетевого парсинга эффективны потоки и асинхронный подход, так как они позволяют не блокировать выполнение во время ожидания ответа от внешних сайтов.
